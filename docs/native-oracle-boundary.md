# Ordinary product and explicit original oracles

The application imports `src/engine.mjs` directly. Its World owns the ordinary
task graph, current JS/KCS VM bytes, native handle identities, input and window
data, decoded images/media and platform/module metadata. Ordinary checkpoints
contain those owners and aliases and do not contain an original process heap.
The pure JavaScript x87 precision operations remain ordinary mathematics.

Original executable loading, Win32 traps, C++ object projections, x86 execution,
Unicorn, original V8 and raw process checkpoints live under `oracle/`. The
explicit `web/transitional-entry.mjs` composition installs their factories and
checkpoint hooks on its actual World. It does not create a replacement ordinary
registry, text runtime, bitmap table, VM or media owner. The original adapters
borrow the corresponding ordinary owner where the current implementation does.

The standalone builder follows the actual application's local ESM graph and
declared asset dependencies. It copies neither all `src`/`web` nor the explicit
oracle include list. It validates both the planned and actual distribution,
rejecting original execution paths, executable inputs and Unicorn artifacts.
Public zlib, FreeType and the pinned OFL font and their corresponding legal
sources remain present. Immutable executable version resources remain data;
their presence does not grant an execution capability or unknown ABI admission.

This source split is a candidate until the remaining SDK integration gates and
formal Stage 10 acceptance. Owned short tests and a dependency/build audit do not
replace SDK tutorial cases, a full campaign or performance acceptance.

Remaining mixed consumers cross one explicit adapter interface rather than
retaining raw process reads, original feature factories or instruction entry
addresses in their ordinary handlers. Missing original-only capabilities fail
explicitly. JS-owned buffer addresses, descriptor reference counts and VM
`sourceRef` regions remain real ordinary data and are not treated as CPU heaps.

Bitmap destination zero uses the ordinary renderer's existing VRAM, texture
pages and bitmap owner. Its clipped source-offset geometry is the same accepted
projection used by the explicit original renderer; no substitute display target
or image table is introduced. The original adapter retains its actual native
upload plus shared-owner projection when explicitly selected.

The generated migration inventory and EXE-address scanner use the same actual
ordinary ESM source graph as the product boundary. The explicit oracle include
list serves only explicit development/oracle consumers. Every selected source
keeps its raw syntactic address/call/reference counts. An implementation label
describes the ordinary registration path and does not turn an unsupported input
or untested business scenario into a pass. Oracle-only groups with no selected
runtime module are absent rather than representing shipped execution.

The executable table locations and image identities used by physical verifiers
are exported only by `oracle/executable-catalog.mjs`. The ordinary catalog derives
its entries from the registered semantic ABI tables; it exports no image/table
VA map. The same original table bytes remain available to explicit oracle
consumers. This does not add a version or admit an unknown slot.

The conservative lexical scanner still counts four ordinary values within the
old image range: three 10,000,000-tick-per-second HAP media timebases and the
little-endian PVL sound-envelope file magic. These data values remain unchanged
and counted. They are not executable addresses, and no exemption directive is
used to turn their count into zero. The complete ordinary source graph and
artifact have no original process/CPU loader dependency; the lexical count and
actual dependency classification are reported separately.

Checkpoint import validates its current composition before changing owners or
performing restore I/O. A non-null/undefined `nativeEngine` input payload requires
an explicitly selected adapter that recognizes that checkpoint and implements
its restore hook. Normal Core cold initialization, live restore, and direct
World restore share this rule. An ordinary checkpoint may omit the field or
carry null; a physical checkpoint cannot succeed by silently discarding its
opaque process data. The guard reads the serialized input tag, not a live process
member. Its one explicit raw member reference remains visible in source audits.

An explicit adapter can restore a fresh physical owner; the owner need not
already be open when composition is validated. The original restore hook still
receives the actual payload exactly once. This is the current shared checkpoint
contract, without another format version or a legacy snapshot reader.
