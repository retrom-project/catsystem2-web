# 问题定位

先固定内容，再复现错误。不要在分析过程中替换 SDK、游戏 EXE、E-mote DLL 或资源归档。
官方 SDK 和目标游戏引擎是两个独立对照：SDK 的构建号不能替代某个游戏实际使用的构建号。
SDK 对照指纹在 `references.json`；游戏对照由私有 fixture manifest 及解包记录管理。

## 捕获浏览器事实

记录 `player.diagnostics()`：游戏内容指纹、FES 栈、CST 场景／行号、最近命令、KCS native 调用、
未识别行为和无效对象引用。保存问题前的状态，在新实例恢复后重放相同输入。
截图和日志放在忽略的本地证据目录，不提交游戏内容。

格式问题用 `npm run corpus -- <game> --decode` 先检查归档、脚本和解码。图像与模型问题分别检查 HG 帧、
E-mote profile、变量和 draw list，区分内容解码、姿态计算、GPU 变形及最终合成。
脚本问题检查 FES 标签和调用栈、CST 位置、共享变量、`\@` 继续消息和语音 tag 时标。
音频问题同时检查浏览器音频上下文、实际解码数据、通道位置与音量。
如果脚本引用没有对应资源的音频，`diagnostics().warnings` 会保留名称，剧情继续静音运行。
不要将资源缺失与浏览器解码失败混为一谈，也不要为了消除警告而改写冻结的原始资源。

FES 对不存在对象的操作继续执行，并单独记录 `warnings`；未知操作进入 `unsupported`。
不能因为调用被记录、VM 继续执行或标题已显示，就认为相关功能已实现。

## 原生对照

使用已经脱壳并校验指纹的游戏 EXE 和配套 E-mote DLL。优先打开已冻结的 IDA 数据库，
对照脚本命令分派、KCS native 编号、参数次序和变量读写。关键切点包括：

| 切点             | native 编号       | 浏览器实现                        |
| ---------------- | ----------------- | --------------------------------- |
| 读／写编号变量   | `0xD2` / `0xD3`   | BootHost / FES context            |
| 写／读字符串变量 | `0x114` / `0x115` | BootHost / shared strings         |
| 加载 CST         | `0x145`           | 启动 VM 停靠后由 ScenePlayer 接管 |
| 启动 FES         | `0x1BF`           | FESPlayer                         |

这些编号来自固定对照和脚本用法，不能作为其他版本的绝对函数地址。
对不清楚的行为建立最小脚本／资源用例，比较原生与浏览器的参数及状态，
确认后在最近确定的边界补回归，再重跑真实游戏路径。

`references.json` 另记录游戏引擎 2.6.1.76 的 SHA-256 与静态切点。
例如 FES 帧循环 `0x756900` 通过 `0x769860` 分派命令，`next` 的处理器是 `0x77A580`。
它切换标签后在当前帧继续取指；在此处人为插入一帧，会使基于 `_CLICK_L_` 的按钮漏掉点击。
缺失的 `call` 目标按空子程序返回，并留下警告；不存在的对象引用也保留为警告。
这两类行为分别有不依赖游戏素材的脚本回归，原生存读档面板则负责验证完整交互链。
可从[官方 next](https://cs2.suki.jp/manual/fes/reference/cn/next.html)、
[wait](https://cs2.suki.jp/manual/fes/reference/cn/wait.html) 和
[系统变量](https://cs2.suki.jp/manual/fes/code/sysvar.html) 文档核对命令契约，再用匹配二进制补齐时序细节。

原生 EXE／DLL 的动态对照、逐帧视觉差异、任意第三方 PPI 和全部 KCS native 的覆盖
是独立验证项；格式解析或主线快进通过不能替代它们。
